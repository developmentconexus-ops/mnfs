# M1.9 — Real Pi + Lavish Browser Pilot

**Environment:** Ubuntu on WSL2, Windows browser host  
**Branch:** `feat/m1-visual-planning`  
**Purpose:** prove the complete human-in-the-loop planning flow before M1 is merged.

## Pilot mission

Use MNFS to produce and approve the execution contract for the smallest M2 vertical slice:

> A Pi worker receives one approved feature contract, works in one leased Treehouse worktree, writes a durable CLAIM, and the lead can recover that claim after restart. Herdr remains optional presentation and must not be lifecycle authority.

This is planning only. Do not implement M2 during this pilot.

## Preconditions

From the repository root:

```bash
git switch feat/m1-visual-planning
git pull --ff-only
npm run verify
command -v pi
command -v lavish-axi || npm install -g lavish-axi
node bin/mnfs.mjs doctor
```

`doctor` must remain READY. Lavish must resolve on `PATH` before starting the skill.

## 1. Open the dogfood mission

```bash
node bin/mnfs.mjs mission open \
  --goal "Design the smallest M2 one-worker slice: Pi worker, Treehouse lease, durable CLAIM and lead restart recovery; Herdr optional" \
  --json | tee /tmp/mnfs-m1.9-mission.json

MISSION_ID=$(jq -r '.id' /tmp/mnfs-m1.9-mission.json)
echo "$MISSION_ID"
```

Keep the printed mission ID for every later check.

## 2. Start Pi and invoke the project skill

```bash
pi
```

Inside Pi:

```text
/reload
/skill:mnfs-plan
```

Tell Pi:

```text
Use mission <MISSION_ID>. Plan the smallest M2 one-worker vertical slice described by the mission goal. Do not implement anything.
```

Expected behavior:

1. Pi inspects mission/status and current planning state.
2. Pi writes a complete temporary JSON plan.
3. MNFS saves revision 1.
4. MNFS renders the HTML artifact.
5. Lavish opens the local artifact in the Windows browser.
6. Pi remains attached to `plan poll` waiting for feedback.

## 3. Request one concrete change in Lavish

In the Lavish browser, send this exact product decision:

```text
Make Herdr explicitly optional and remove it from every deciding acceptance criterion. The deciding M2 proof must be: one Pi worker uses a leased Treehouse worktree, writes a durable CLAIM, and a restarted lead recovers it without transcript or terminal parsing.
```

Do not approve revision 1.

Expected behavior:

1. Pi receives the feedback through `plan poll`.
2. Pi updates the full structured JSON, preserving unrelated content.
3. Pi saves revision 2 with revision 1's exact `--expected-hash`.
4. The content hash changes.
5. Pi reopens revision 2 in Lavish.

## 4. Approve the exact second revision

Review the updated plan. Confirm that:

- Herdr is optional presentation only;
- Pi worker execution is included;
- Treehouse lease/worktree is included;
- durable CLAIM is included;
- lead restart recovery is included;
- transcript/terminal parsing is not the source of truth;
- no implementation work was started.

Use the rendered **Approve this exact hash** control in Lavish. It must queue a token of this form:

```text
MNFS_APPROVE_PLAN mission=<MISSION_ID> hash=sha256:<CURRENT_HASH>
```

Expected behavior:

1. Pi reloads current plan state.
2. Pi verifies the mission and exact hash.
3. Pi confirms no blocking question remains open.
4. Pi calls `plan approve` with that exact hash.
5. MNFS materializes `.mnfs/missions/<MISSION_ID>/plan.json`.

## 5. Independent recovery proof

Exit Pi completely. In a fresh shell process:

```bash
MISSION_ID=<MISSION_ID>

node bin/mnfs.mjs plan show \
  --mission "$MISSION_ID" \
  --json | tee /tmp/mnfs-m1.9-approved.json

APPROVED_HASH=$(jq -r '.contentHash' /tmp/mnfs-m1.9-approved.json)
CONTRACT_HASH=$(jq -r '.contentHash' ".mnfs/missions/$MISSION_ID/plan.json")
STATUS=$(jq -r '.status' /tmp/mnfs-m1.9-approved.json)
REVISION=$(jq -r '.revision' /tmp/mnfs-m1.9-approved.json)

printf 'status=%s revision=%s approved=%s contract=%s\n' \
  "$STATUS" "$REVISION" "$APPROVED_HASH" "$CONTRACT_HASH"

test "$STATUS" = "APPROVED"
test "$REVISION" -ge 2
test "$APPROVED_HASH" = "$CONTRACT_HASH"
```

## 6. Version the accepted contract

```bash
git status --short
git add ".mnfs/missions/$MISSION_ID/plan.json"
git commit -m "docs: approve M2 one-worker mission plan"
git push origin feat/m1-visual-planning
```

Do not commit temporary JSON or runtime HTML artifacts.

## Acceptance record

M1.9 passes only when all are true:

- [ ] Pi discovers and executes `/skill:mnfs-plan`.
- [ ] Lavish opens in the Windows browser from the WSL process.
- [ ] Revision 1 is created and shown.
- [ ] Operator feedback causes revision 2.
- [ ] Revision 2 has a different hash.
- [ ] Pi uses revision 1's exact previous hash when saving revision 2.
- [ ] Approval originates from the exact current-hash Lavish control.
- [ ] `.mnfs/missions/<id>/plan.json` contains the approved hash.
- [ ] A fresh CLI process recovers `APPROVED` revision 2 or later.
- [ ] The approved contract is committed and pushed.

## Stop conditions

Stop instead of improvising when:

- `lavish-axi` cannot open through Windows localhost;
- Pi edits HTML, SQLite or the approved contract directly;
- Pi starts implementation or worker execution;
- revision 2 is saved without `--expected-hash`;
- approval occurs without the exact current-hash token;
- a blocking question remains open;
- the fresh-process hash differs from the materialized contract hash.
