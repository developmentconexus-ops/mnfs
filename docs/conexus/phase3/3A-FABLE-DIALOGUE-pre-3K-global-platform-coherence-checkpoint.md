## 8. Complexity / YAGNI audit

At first glance the architecture is large:

```text
15 domain/module boundaries
46 durable record classes
multiple state lifecycles
strong security/recovery laws
```

But complexity must be judged by whether it is essential or accidental.

### Essential complexity that has a real owner/failure class

Examples:

```text
I&A                  → actual tenant/user authority
Workspace            → company/tenant root
Project              → software lifecycle unit
Builder              → software evolution
Registry             → immutable executable definitions
Connections          → reusable external-system binding/credential lifecycle
Gateway              → external/business effect authority
Brain                → cross-Project organizational meaning
PAR                  → Product Agent durable authority
Release              → exact promoted composition
OBS                  → audit/evidence without stealing domain truth
Attachments          → private content custody
MAR                  → real MANAGED serving path
```

The records are physically kept inside one `hub_control` database and modules remain one modular monolith. The design intentionally rejects microservices, workflow engines, policy engines, generic resource graphs, event sourcing, K8s, HA and future-scale machinery.

Checkpoint judgment:

> **The internal model is sophisticated, but not presently overengineered relative to the declared product/trust/effect/recovery problem. The greater risk is PRODUCT-SURFACE complexity, not backend module count.**

### Product-surface guardrail for 3K

The Golden Path must not make a normal user understand:

```text
WorkUnit IDs
ActorRun internals
TxScope
Tier-2 FKs
Promotion FSM steps
producer_trust taxonomy
RPO mechanics
DB role partitioning
```

unless that detail is useful for diagnosis/advanced operation.

A simple build/change should feel closer to:

```text
Describe intent
→ Conexus understands/discovers
→ concise review/approval
→ builds visibly
→ preview
→ publish
```

not:

```text
fill architecture/governance forms
→ manage internal state machines
→ manually coordinate workers
```

C-017 allows this because `FAST` checkpoint is compact and PlanningDepth can be DIRECT. 3K must make that true in the product.
