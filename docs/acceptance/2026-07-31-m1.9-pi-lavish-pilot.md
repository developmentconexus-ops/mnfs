# M1.9 — Corrected Pi + Lavish Browser Retest

**Environment:** Ubuntu on WSL2, Windows browser host  
**Branch:** `feat/m1-visual-planning`  
**Purpose:** close M1 after the original pilot proved the core flow but exposed review-session churn and a raw Mermaid dependency block.

The approved M2 contract already exists at:

```text
.mnfs/missions/MIS-002/plan.json
```

Do not replace or reapprove that contract. This retest validates only the corrected visual behavior.

## 1. Preconditions

```bash
git switch feat/m1-visual-planning
git pull --ff-only
npm run verify
command -v pi
command -v lavish-axi
node bin/mnfs.mjs doctor
```

Required:

- verification green;
- `doctor` READY;
- Pi and Lavish available.

## 2. Confirm the approved plan renders as SVG

```bash
node bin/mnfs.mjs plan render --mission MIS-002 --json \
  | tee /tmp/mnfs-m1.9-fixed-render.json

jq '{htmlPath, snapshotPath, revision: .revision.revision, hash: .revision.contentHash}' \
  /tmp/mnfs-m1.9-fixed-render.json

node bin/mnfs.mjs plan open --mission MIS-002 --json
```

In the Windows browser, confirm:

- the dependency panel contains boxes and arrows;
- milestone and feature IDs/titles are visible;
- raw `flowchart LR` text is not visible;
- the URL/session corresponds to the stable `review.html` artifact.

End that approved-plan review from the browser or close the tab before the continuity test.

## 3. Create a disposable continuity mission

```bash
node bin/mnfs.mjs mission open \
  --goal "Retest one persistent Lavish review session across two plan revisions with a visible dependency SVG; planning only" \
  --json | tee /tmp/mnfs-m1.9-continuity-mission.json

MISSION_ID=$(jq -r '.id' /tmp/mnfs-m1.9-continuity-mission.json)
echo "$MISSION_ID"
```

## 4. Start Pi and create revision 1

```bash
pi
```

Inside Pi:

```text
/reload
/skill:mnfs-plan
```

Then:

```text
Use mission <MISSION_ID>. Create a minimal two-feature planning contract where F02 depends on F01, so the dependency SVG is visible. Planning only; do not implement.
```

Expected:

1. Pi creates revision 1.
2. Pi runs `plan open` once.
3. Lavish opens one Windows browser tab at the stable `review.html` path.
4. Pi waits on `plan poll`.

## 5. Request one revision without reopening

In the Lavish conversation, send:

```text
Rename F02 to "Recovered review context" and keep F02 dependent on F01. Change nothing else.
```

Expected Pi behavior:

1. save revision 2 with revision 1's exact `--expected-hash`;
2. run `plan render --mission <MISSION_ID> --json`;
3. do **not** run `plan open` again;
4. continue `plan poll` on the same stable path.

Browser acceptance:

- the same tab live reloads;
- the prior conversation remains visible;
- no second Lavish session/tab opens;
- the SVG updates and shows the renamed F02 node;
- raw Mermaid source never appears.

## 6. Approve the exact revision

Use **Approve this exact hash** in the same browser session.

Expected:

- Pi performs a fresh `plan show`;
- Pi approves only the exact current hash;
- `.mnfs/missions/<MISSION_ID>/plan.json` is materialized.

## 7. Fresh-process proof

Exit Pi and run:

```bash
node bin/mnfs.mjs plan show --mission "$MISSION_ID" --json \
  | tee /tmp/mnfs-m1.9-fixed-approved.json

STATUS=$(jq -r '.status' /tmp/mnfs-m1.9-fixed-approved.json)
REVISION=$(jq -r '.revision' /tmp/mnfs-m1.9-fixed-approved.json)
APPROVED_HASH=$(jq -r '.contentHash' /tmp/mnfs-m1.9-fixed-approved.json)
CONTRACT_HASH=$(jq -r '.contentHash' ".mnfs/missions/$MISSION_ID/plan.json")

printf 'status=%s revision=%s approved=%s contract=%s\n' \
  "$STATUS" "$REVISION" "$APPROVED_HASH" "$CONTRACT_HASH"

test "$STATUS" = "APPROVED"
test "$REVISION" -ge 2
test "$APPROVED_HASH" = "$CONTRACT_HASH"
```

## 8. Keep the repository clean

This mission exists only to prove the fix. Do not commit its approved contract:

```bash
rm ".mnfs/missions/$MISSION_ID/plan.json"
git status --short
```

The existing approved `MIS-002` contract remains the versioned M2 plan.

## Stop conditions

Stop and report instead of improvising when:

- a second Lavish session/tab opens for revision 2;
- conversation history disappears;
- raw Mermaid text remains visible;
- Pi invokes `plan open` after the first revision;
- revision 2 is saved without `--expected-hash`;
- approval occurs without the exact current-hash token;
- Pi edits HTML, SQLite or a contract directly;
- the final approved hash differs from the materialized contract hash.
